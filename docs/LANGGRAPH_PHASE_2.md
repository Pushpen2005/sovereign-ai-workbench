## 2. Adapter Architecture

The adapter boundary is located in [`backend/src/orchestration/inspection/inspection.adapters.js`](file:///Users/pushpentiwari/sovereign-ai-workbench/backend/src/orchestration/inspection/inspection.adapters.js).

```
   ┌─────────────────────────────────────────────────────────────┐
   │                   LangGraph StateGraph                      │
   │      (Pure State Machine: Sequencing, Errors, Lifecycle)    │
   └───────────────┬─────────────────────────────┬───────────────┘
                   │                             │
                   ▼                             ▼
       ┌───────────────────────┐     ┌───────────────────────┐
       │ InspectionAgentState  │     │       Graph Nodes     │
       │ (14 Typed Channels)   │     │ (ingest, retrieve...) │
       └───────────────────────┘     └───────────┬───────────┘
                                                 │
                                                 ▼
             ┌───────────────────────────────────────────────────────┐
             │       Service Adapter Boundary (inspection.adapters)  │
             │ - runIngestion()            - runRiskAssessment()     │
             │ - runRetrieval()            - runCitationValidation() │
             │ - runFindingsExtraction()   - runReportGeneration()   │
             │ - runSopRetrieval()                                   │
             └───────────────────────────┬───────────────────────────┘
                                         │
                                         ▼
┌─────────────────────────────────────────────────────────────────────────────────┐
│                       Existing SovereignAI Core Services                        │
│ - Qdrant Vectorstore (Cosine 384)   - Local ONNX Embeddings (all-MiniLM-L6-v2) │
│ - Local Ollama (llama3.2:3b)        - python-docx Approval Note Script         │
│ - Tesseract OCR Fallback            - PostgreSQL Multi-tenant Tables           │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### Key Architectural Guarantees:
1. **No Logic Duplication:** The adapters invoke existing tested methods directly. There are zero duplicate prompt templates, zero duplicate Qdrant filters, and zero duplicate embedding calls.
2. **Strict SOP Knowledge Base Isolation:** `runSopRetrieval()` enforces `documentType="sop"`. Inspection documents can never be retrieved or treated as authoritative standard operating procedures.
3. **Anti-Hallucination Citation Verification:** `runCitationValidation()` ensures that any citation generated by the LLM is checked against the actual retrieved SOP chunks. Fabricated citations are discarded.
4. **Zero Findings Safety:** If 0 findings are detected, `assessRiskNode` provides safe defaults (`level: null`, `reason: "No significant inspection findings were detected..."`) without invoking the LLM to invent nonexistent risks.
5. **Dependency Injection & Testability:** All adapters accept options allowing mocked embedding, retrieval, LLM, or file generation functions for deterministic CI testing without live Ollama/Qdrant dependencies.

## 4. Graph Execution Example

### Input State:
```json
{
  "runId": "run-e2e-uuid-101",
  "documentId": "doc-adapter-test-001",
  "task": "Analyze Pump-03 bearing temperature inspection findings.",
  "organizationId": "0bd5dba2-05e1-4f5c-9047-25843d338622",
  "metadata": { "env": "production" }
}
```

### Execution Flow:
1. `ingest`: Ingests/indexes document; stores `chunksStored: 12`.
2. `retrieve`: Runs 3 multi-aspect domain queries; retrieves and deduplicates chunks.
3. `extract_findings`: Analyzes chunks using local LLM; extracts finding for Pump-03 bearing temperature (92°C vs 80°C limit, severity HIGH).
4. `retrieve_sop`: Queries SOP collection with `documentType: "sop"`; retrieves `Demo_Maintenance_SOP.pdf`.
5. `assess_risk`: Evaluates finding against SOP; rates risk `HIGH` due to 12°C limit exceedance; formulates recommendation.
6. `validate_citations`: Validates that citation references chunk in `Demo_Maintenance_SOP.pdf`; discards any invalid citations.
7. `generate_report`: Spawns `generate_docx.py`; creates `Approval_Note_doc-adapter-test-001.docx`; registers record in PostgreSQL `reports` table.

## 5. Error Handling & Downstream Halting

Every node is wrapped in an explicit failure boundary:
- When a node fails (e.g., Qdrant network failure or missing document ID), the node catches the error, appends an error record `{ node, message, timestamp }` to `errors`, and transitions `status: "failed"`.
- All downstream nodes inspect `state.status === "failed" || state.errors.length > 0` before running.
- If the workflow has failed, downstream nodes record their execution footprint and immediately return without attempting to process missing data or calling downstream services.
- The workflow completes safely without unhandled Node.js promise rejections or process crashes.

## 8. Migration Readiness (Phase 3 Roadmap)

With Phase 2 complete, the LangGraph inspection pipeline is fully connected, tested, and ready for production cutover when approved:
1. **Internal Delegation:** `runCompleteWorkflow()` in `inspection.service.js` can be refactored into a single line calling `compiledInspectionGraph.invoke(initialState)`.
2. **State Checkpointing:** A LangGraph checkpointer (e.g. `MemorySaver` or PostgreSQL checkpointing) can be attached to provide resumption across long-running tasks.
3. **Human-in-the-Loop Node:** An approval interrupt can be inserted between `validate_citations` and `generate_report` to allow human review before executive DOCX compilation.
